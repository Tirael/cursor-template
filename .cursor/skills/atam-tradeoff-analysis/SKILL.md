# ATAM / Architecture Tradeoff Analysis (Skill)

## Когда применять

- Есть 2+ архитектурных варианта и нужно обоснованно выбрать
- Нужно проверить, выдержит ли архитектура критические NFR/SLO до начала реализации
- Требуется зафиксировать компромиссы (trade-offs) и риски перед ADR

## Входы (SSOT и артефакты)

- Core принципы: `.cursor/rules/project-core.mdc` (v1.0, 2026-02-04)
- Core NFR: `.cursor/rules/nfr-core.mdc` (v1.0, 2026-02-04)
- Полные NFR (если есть): `nfr-requirements.md`
- Каталог компромиссов: `tradeoffs.md`
- Диаграммы: `src/c4/` (C4), `src/diagrams/` (PlantUML)

## Выходы

- Топ бизнес-драйверов и ограничений (5–10 пунктов)
- Набор измеримых quality-attribute scenarios
- Utility tree (атрибут → сценарий → приоритет/сложность)
- **Sensitivity points** (параметры/решения, к которым “чувствительны” метрики)
- **Tradeoff points** (точки, где улучшение одной характеристики ухудшает другую)
- Список **risks / non-risks** + рекомендации (mitigations/эксперименты)
- Фиксация решений: `adr-architecture-decisions.md` и/или уточнения в `tradeoffs.md`

## Процесс (упрощённый ATAM)

1. Определить границы анализа: что в scope/out of scope, какие варианты сравниваем.
2. Зафиксировать бизнес-драйверы и ограничения (включая регуляторные/безопасность/эксплуатацию).
3. Собрать quality-attribute scenarios по шаблону ниже (20–40 штук, затем сократить).
4. Построить utility tree и приоритизировать сценарии:
   - приоритет: H/M/L (ценность и критичность)
   - сложность: H/M/L (стоимость/риск реализации)
5. Для каждого варианта архитектуры описать подходы/тактики, которыми он закрывает сценарии.
6. Пройтись по топ-сценариям и для каждого определить:
   - какие компоненты/интеграции задействованы
   - какие метрики/лимиты проверяем (p95, RTO/RPO, error rate)
   - где возможна деградация/отказ и как это проявится
7. Выявить sensitivity points и tradeoff points, выписать risks/non-risks.
8. Сформировать mitigations: изменения архитектуры, конфигурации, прототипы (spikes), измерения.
9. Выбрать вариант и зафиксировать решение с последствиями (что выигрываем / что теряем).

## Чек-лист качества результата

- Сценарии **измеримы** и привязаны к Core NFR (`.cursor/rules/nfr-core.mdc`).
- Учтены **неизменные правила**: `tenantId` (изоляция данных), ABAC, `audit_log`, Vault, mTLS для gRPC, outbox для событий, retry/backoff + circuit breaker, async для операций >5 сек.
- Для каждого trade-off сформулировано “что выигрываем / что теряем” и кого это затрагивает.
- Для high-risk пунктов есть конкретные mitigations и список проверок/экспериментов.
